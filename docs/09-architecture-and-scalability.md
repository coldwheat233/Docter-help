# 09 - 系统架构 & 高并发设计

> 解决两个问题：
> 1. **系统在医疗流程中的位置** —— 我们是"挂号前的智能对话层"，不碰核心 HIS
> 2. **如何抗住多用户并发** —— 分层防御 + 用户无感

---

## 一、系统在医疗流程中的位置

```
患者 → 互联网 → [CDN/WAF]
              │
              ▼
┌──────────────────────────────────────────────────────┐
│  Layer 4: 接入层                                       │
│  - Nginx 负载均衡 / WebSocket / CDN                    │
└──────────────────┬───────────────────────────────────┘
                   ▼
┌──────────────────────────────────────────────────────┐
│  Layer 3: 智能体应用层 ← 【我们做的】                  │
│  - LangGraph Supervisor + 4 Agent + Knowledge          │
│  - 流式响应 / 输入护栏 / 急诊识别                      │
│  - HITL interrupt 把门                                 │
│  - 简化预约 DB（SQLite/PostgreSQL）                    │
│  状态: 挂号前的智能对话                                  │
│  职责: 问诊收集 / 时段推荐 / 医学知识问答               │
│  **不**做: 病历 / LIS 报告 / 财务 / 医保                │
└──────────────────┬───────────────────────────────────┘
                   ▼ (调用医院 API)
┌──────────────────────────────────────────────────────┐
│  Layer 2: 医院核心 HIS 系统（**我们不做的**）          │
│  - 患者主索引（EMR）                                  │
│  - 排班主数据（Master Schedule）                        │
│  - 财务/医保结算                                       │
│  - 医生工作站                                         │
└──────────────────┬───────────────────────────────────┘
                   ▼
┌──────────────────────────────────────────────────────┐
│  Layer 1: 临床/检验系统                                 │
│  - LIS（检验） / PACS（影像） / EMR（病历）             │
└──────────────────────────────────────────────────────┘
```

**关键设计**：
- **不**碰核心 HIS（避免合规风险 + 系统耦合）
- 预约最终落库到我们的**简化预约 DB**（SQLite/PostgreSQL）
- HIS 通过 API 同步（每天 N 次或实时 webhook）
- 我们是"对话界面"层，HIS 是"权威数据"层

## 二、并发风险与防御

### 当前架构的并发风险

| 风险 | 严重度 | 当前状态 | 解决方案 |
|---|---|---|---|
| DeepSeek API 限流 | 🔴 高 | 无保护 | 全局限流 + 熔断（已做 CircuitBreaker） |
| 100 用户问"感冒发烧" | 🟡 中 | 100 次 LLM 调用 | **响应缓存**（v3 新增 ✅） |
| 1 用户 100 次/秒 | 🟡 中 | 无保护 | **用户级限流**（v3 新增 ✅） |
| SQLite 写锁等待 | 🟡 中 | 单文件 | 写少 / 乐观锁（已做） |
| Streamlit 单进程 | 🟡 中 | 1 进程 | 多 worker / K8s |
| InMemorySaver 重启丢状态 | 🟠 中 | 内存 | PostgresSaver（v2 周做） |
| WebSocket 断线 | 🟢 低 | 部分 | 重连机制 |

### 用户无感的 4 个维度

| 维度 | 含义 | 实现 |
|---|---|---|
| **排队无感** | 用户感受不到"前面有 N 人" | 响应缓存（命中走快速路径） |
| **延迟无感** | 流式响应，不等全部完成 | `st.write_stream` + LLM streaming |
| **失败无感** | API 挂了自动 fallback | 熔断 + OpenAI 备用 |
| **重复无感** | 同问同答秒回 | 响应缓存（v3 新增 ✅） |

## 三、已实现的高并发手段

### 1. 响应缓存（v3）

**位置**：`src/medical_agent/cache.py`

**机制**：
- LRU + TTL（默认 5 分钟、500 条）
- query 归一化（去标点/空格/小写）
- 线程安全
- 命中统计（hit_rate）

**效果**：
- 100 用户问"感冒发烧" → 1 次 LLM 调用
- 节省 token + 立即响应
- **不含用户特定字段**（patient_id/appointment_id 不入缓存）

### 2. 用户级限流（v3）

**位置**：`src/medical_agent/rate_limit.py`

**机制**：
- 滑动窗口（默认 10 req/min/user）
- 线程安全
- 用户间隔离
- 超限返回"系统繁忙，请稍后再试"（不暴露内部）

**效果**：
- 防止单用户滥用
- 减少雪崩风险
- 友好提示（无感保护）

### 3. 熔断器（已有 v1）

**位置**：`src/medical_agent/resilience.py`

**机制**：
- 5 次连续失败 → OPEN
- 60 秒后 HALF_OPEN 探测
- 主 LLM 失败 → OpenAI 备用

**效果**：
- DeepSeek 挂了自动切 OpenAI
- 用户看到"系统正在用备用模型"（无感）

### 4. 乐观锁（v1 + v2 增强）

**位置**：`src/medical_agent/db/repositories.py`

**机制**：
- `version` 字段 + CAS
- 100 并发预约同一时段 → 1 成功 99 收到 `OPTIMISTIC_LOCK` 错误

**效果**：
- 不会双重预约
- 失败用户看到"该时段已满，请重选"

## 五、未来架构演进路线

### 阶段 1：单实例（当前）
```
用户 → Streamlit → LangGraph → DeepSeek
                  ↓
                SQLite
```
**容量**：~10 RPS，~100 并发用户

### 阶段 2：多实例 + 异步化
```
用户 → Nginx → [Streamlit × N] → [Worker × M] → DeepSeek
                                  ↓
                                Redis (cache + queue)
                                  ↓
                                PostgreSQL (主从)
```
**容量**：~100 RPS，~1000 并发用户

### 阶段 3：K8s 弹性
```
用户 → CDN → [K8s pod × 动态] → [Worker pool] → LLM
                                          ↓
                                       消息队列
                                          ↓
                                       PostgreSQL cluster
```
**容量**：~10000 RPS，~100K 并发用户

## 六、Web 端抗并发设计

### 当前 Web 端（Streamlit 单进程）

**问题**：
- 单进程 100 WebSocket 排队
- 重启丢所有 session

**临时方案**（v3 已做）：
- **响应缓存**：减少 80% LLM 调用
- **用户级限流**：防单用户滥用
- **急诊识别短路**：减少紧急情况下的 LLM 调用

**生产化方案**：
- **FastAPI + async**：替代 Streamlit
- **WebSocket 断线重连**
- **多 worker（gunicorn -w 4）**

## 七、用户无感设计原则

| 原则 | 实现 |
|---|---|
| **同问同答秒回** | 响应缓存 + 关键词归一化 |
| **流式不卡顿** | `st.write_stream` + Server-Sent Events |
| **失败自动降级** | 熔断 + 备用模型 |
| **重试不打扰** | idempotency_key + 乐观锁 |
| **变更不感知** | Prompt 版本管理 + 灰度发布（YAML） |
| **急诊不延迟** | 急诊识别短路（不调 LLM） |
| **限流不粗暴** | "系统繁忙请稍后再试"+ 倒计时（不是 429 错误页） |
| **保护不泄密** | 输出过滤：error_code 不给用户看 |
